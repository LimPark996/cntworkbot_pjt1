# RAG 시스템 구축 실습 교육 과정 (4일)

> **대상:** 비전공자 (프로그래밍 경험 없거나 초급)  
> **목표:** PDF 법령 문서를 활용한 AI 챗봇의 전체 파이프라인을 직접 구현하며 이해하기  
> **방식:** 이론 설명 → 함수 단위 실습(ToDo) → 클래스 통합 → 실행 및 검증  
> **구성:** 팀 5명 (팀장 겸 강사 1명 + 팀원 4명)

---

## 교육 설계 철학

1. **단계별 점진적 난이도** — 파일 I/O부터 검색 알고리즘까지, 매일 한 단계씩 복잡도 증가
2. **즉시 실행 가능** — 각 ToDo를 완성하면 바로 결과 확인 가능
3. **실무 연결** — 단순 이론이 아닌, 실제 법령 데이터로 작동하는 시스템 구축
4. **빈칸 채우기 방식** — 코드 전체를 작성하는 것이 아니라, 핵심 로직을 직접 구현

## Day 1: PDF 파서 + 문서 통합 (`s1`, `s2`)

### 학습 목표
- Python 함수와 클래스의 기본 구조 이해
- 파일 I/O (PDF 읽기, JSON 쓰기/읽기)
- 에러 처리 (try-except)
- 다중 문서를 하나의 통합 구조로 병합

### 핵심 개념
- **RAG의 첫 단계:** AI가 답변하려면 먼저 문서를 읽을 수 있어야 한다
- pdfplumber 라이브러리로 PDF의 텍스트를 페이지별로 추출
- **왜 통합이 필요한가:** 9개 법령 PDF를 각각 검색하면 비효율 → 하나의 데이터베이스로 통합

### 실습 구성

**오전 — S1: PDF 파서 (ToDo 6개)**

| # | 실습 내용 | 배우는 것 |
|---|-----------|-----------|
| 1 | `open_pdf()` — PDF 파일 열기 | 라이브러리 사용법 |
| 2 | `create_page_data()` — 페이지 데이터 구조화 | dict 자료구조 |
| 3 | `create_document_info()` — 문서 메타데이터 생성 | 데이터 설계 |
| 4 | `parse_all_pages()` — 전체 페이지 순회 | 반복문, 에러 처리 |
| 5 | `save_to_json()` — JSON으로 저장 | 파일 I/O |
| 6 | `process_pdf_file()` — 전체 연결 | 함수 조합 |

**오후 — S2: 문서 통합기 (ToDo 6개)**

| # | 실습 내용 | 배우는 것 |
|---|-----------|-----------|
| 1 | `get_json_files()` — 파일 목록 가져오기 | 파일 탐색, 필터링 |
| 2 | `load_json_file()` — JSON 파일 읽기 | 인코딩, 파일 로딩 |
| 3 | `create_doc_info()` — 문서 정보 구조화 | ID 체계 설계 |
| 4 | `create_metadata()` — 메타데이터 추출 | 요약 정보 생성 |
| 5 | `save_unified_data()` — 통합 데이터 저장 | JSON 쓰기 |
| 6 | `merge_documents()` — 전체 파이프라인 연결 | 워크플로우 설계 |

### 학습 흐름
```
개별 함수 구현 → 테스트 → 클래스로 통합 → 배치 처리 → 문서 통합
```

## Day 2: 법률 청킹 + 임베딩 (`s3`, `s4`)

### 학습 목표
- 토큰(token)의 개념과 LLM 컨텍스트 윈도우 이해
- 정규식(regex)으로 법률 구조 파싱
- 청킹(chunking)이 검색 품질에 미치는 영향
- 임베딩(embedding)의 개념: 텍스트 → 숫자 벡터
- FAISS 벡터 데이터베이스의 원리
- API 비용 절감을 위한 캐싱 전략

### 핵심 개념
- **왜 청킹이 중요한가:** LLM에는 한번에 넣을 수 있는 텍스트 양에 한계가 있다
- **왜 법률 구조를 인식해야 하는가:** "제36조"를 반으로 자르면 의미가 깨진다
- **임베딩이란:** "건축법"과 "건물 관련 법률"이 가까운 벡터로 변환되는 것
- **FAISS란:** 수천 개 벡터에서 가장 가까운 것을 빠르게 찾아주는 도구 (벡터 창고)

### 핵심 알고리즘 (S3)
```
1. 정규식으로 "제N조" 단위 분리
2. 800 토큰 초과 시 "①②③" 항 단위로 재분리
3. 그래도 초과 시 토큰 기반 강제 분할
4. 인접 청크 간 200 토큰 오버랩 적용
```

### 실습 포인트
- tiktoken으로 토큰 수 계산해보기
- 정규식 `제\d+조` 패턴으로 법조문 추출해보기
- OpenAI API로 텍스트를 3072차원 벡터로 변환해보기
- FAISS 인덱스에 벡터를 넣고, 유사한 청크를 검색해보기
- MD5 해시로 캐시 키를 만드는 원리 이해

## Day 3: 검색 엔진 + 질의 분류/답변 생성 (`s5`, `s61`, `s62`)

### 학습 목표
- 정보 검색(Information Retrieval)의 기본 원리
- BM25 키워드 검색과 벡터 검색의 차이
- RRF(Reciprocal Rank Fusion)로 검색 결과 결합
- Cross-encoder 리랭킹의 원리
- GPT 기반 질의 유형 분류 (7종)
- 유형별 맞춤 프롬프트 설계와 Grounding 원칙

### 핵심 개념
- **왜 하이브리드인가:**
  - "제36조" → 키워드 검색이 정확 (벡터는 비슷한 번호를 혼동)
  - "안전 조치" → 벡터 검색이 정확 (키워드는 동의어를 놓침)
  - 둘 다 써야 법률 검색이 완전해진다

- **RRF 공식:** `score = Σ 1/(k + rank)`
  - 각 검색 방식의 순위를 정규화하여 결합

- **Cross-encoder 리랭킹:**
  - (질문, 문서) 쌍을 직접 비교하여 관련성 점수 산출
  - 1차 검색보다 정밀하지만 느려서, 상위 5개에만 적용

- **질의 분류:** "제36조가 뭐야?"와 "체크리스트 만들어줘"는 답변 형식이 완전히 다름
  - GPT-4o-mini로 7종 분류 → 유형별 시스템 프롬프트 적용

### 실습 포인트
- Vector Search 단독 vs BM25 단독 vs 하이브리드 결과 비교
- RRF k 파라미터 조정에 따른 결과 변화 관찰
- Reranking 전후 순위 변화 확인
- 질의 유형별 답변 형식 차이 체험

## Day 4: Streamlit 챗봇 + 보강

### 학습 목표
- Streamlit을 활용한 웹 챗봇 UI 구축
- 전체 파이프라인 통합 (검색 → 분류 → 답변 생성 → 표시)
- Day 1~3에서 어려웠던 부분 복습 및 보강

### 핵심 개념
- **Streamlit:** Python만으로 웹 앱을 빠르게 만들 수 있는 프레임워크
- `st.chat_message`, `st.chat_input`으로 채팅 UI 구현
- `@st.cache_resource`로 FAISS 인덱스, 리랭커 모델 로딩을 세션 간 공유

### 실습 포인트
