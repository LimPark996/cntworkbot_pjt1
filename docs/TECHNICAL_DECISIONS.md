# 기술 의사결정 기록 (Architecture Decision Records)

이 문서는 프로젝트의 주요 기술 선택에 대한 **근거**를 정리한 것입니다.

---

## 1. 청킹 전략: 왜 조(條)/항(項) 단위 계층적 청킹인가?

### 문제
법률 문서를 단순 토큰 수 기반으로 자르면, 하나의 조문이 두 청크에 걸쳐 분리됩니다.  
"제36조 1항"의 전반부와 후반부가 다른 청크에 들어가면, 검색 시 불완전한 정보를 반환합니다.

### 결정
**조(條) → 항(項) → 토큰 순서의 3단계 계층적 분할**을 구현했습니다.

```
1순위: 제N조 단위로 분리 (정규식: 제\d+조)
2순위: 조 내에서 항(①②③ 또는 1.2.3.) 단위로 분리
3순위: 그래도 800토큰 초과 시 토큰 기반 분할
```

### 근거
- 법률은 "제N조 제N항"이 하나의 의미 단위 — 이 경계를 존중해야 검색 정확도가 높음
- 200토큰 오버랩으로 청크 간 문맥 손실 최소화
- tiktoken으로 GPT와 동일한 토크나이저 사용 → 정확한 컨텍스트 윈도우 관리

### 대안 검토
| 방식 | 기각 이유 |
|------|-----------|
| 고정 길이 분할 | 법조문 경계 무시, 의미 단위 파괴 |
| 문장 단위 분할 | 법률 문장이 매우 길어 하나의 문장이 수백 토큰 |
| LLM 기반 분할 | 비용 과다, 속도 느림, 재현성 보장 어려움 |

## 2. 검색: 왜 Vector + BM25 하이브리드인가?

### 문제
법률 QA에서는 두 가지 상반된 검색 니즈가 공존합니다:
- **"제36조가 뭐야?"** → 정확한 키워드 매칭 필요 (Vector Search 약점)
- **"높은 곳에서 일할 때 안전 규정"** → 의미적 유사도 필요 (BM25 약점)

### 결정
**FAISS Vector Search + BM25 Keyword Search → RRF 결합 → Cross-encoder Reranking**

### 근거

**Vector Search (FAISS)만 사용할 경우:**
- "제36조"라는 쿼리에 대해 "제35조", "제37조" 등 의미적으로 유사하지만 다른 조문을 반환할 수 있음
- 임베딩 공간에서 법조문 번호는 가까운 거리에 위치하기 때문

**BM25만 사용할 경우:**
- "작업자 안전을 위한 조치"와 "근로자 보호 방안"이 동일한 의미임에도 키워드 불일치로 검색 실패

**하이브리드 접근:**
- RRF(Reciprocal Rank Fusion, k=60)로 두 검색의 순위를 정규화하여 결합
- 최종 Cross-encoder Reranking으로 (Query, Document) 쌍의 관련성을 직접 평가

### 왜 RRF인가?
- 수식: `score = Σ 1/(k + rank)` — 구현이 단순하고 효과적
- Vector와 BM25의 점수 스케일이 다르므로 점수 합산이 아닌 순위 기반 결합이 적합
- k=60은 논문(Cormack et al., 2009)에서 제안된 경험적 최적값

### 왜 FAISS IndexFlatL2인가?
- 법령 9종 (약 1,500 청크) 규모에서는 근사 검색(IVF, HNSW)이 불필요
- Flat Index = 정확한 최근접 이웃 검색 보장
- 데이터 규모가 커지면 IndexIVFFlat으로 전환 가능

## 3. 리랭킹: 왜 Cross-encoder인가?

### 문제
1차 검색(FAISS + BM25 + RRF) 결과의 상위 5개 중에서도 관련성 순서가 최적이 아닐 수 있습니다.

### 결정
**BAAI/bge-reranker-base** Cross-encoder로 최종 리랭킹

### 근거
- **Bi-encoder** (임베딩 검색): Query와 Document를 **독립적으로** 인코딩 → 빠르지만 정밀도 한계
- **Cross-encoder**: Query와 Document를 **함께** 입력 → 직접 관련성 점수 산출 → 더 정확
- bge-reranker-base는 278M 파라미터로 경량, 한국어 포함 다국어 지원

### 왜 전체 검색에 Cross-encoder를 쓰지 않는가?
- Cross-encoder는 O(N) 비용 (전체 청크와 쿼리를 일일이 비교)
- 1,500개 청크 전체 비교 시 수십 초 소요
- 따라서 1차 검색으로 후보를 5개로 축소 → Cross-encoder는 5개만 비교

## 4. 질의 분류: 왜 7종 유형 분류를 먼저 하는가?

### 문제
"제36조가 뭐야?"와 "안전 체크리스트 만들어줘"는 같은 RAG 파이프라인을 타더라도 **답변 형식이 완전히 달라야** 합니다.

### 결정
GPT-4o-mini로 질의를 7종으로 분류한 뒤, 유형별 맞춤 시스템 프롬프트를 적용

### 근거

| 유형 | 필요한 답변 전략 |
|------|------------------|
| 법조문 조회 | 원문 정확 인용, 해설 추가 |
| 상황별 컨설팅 | 적법/부적법 판단 + 근거 명시, 확실하지 않으면 판단 보류 |
| 문서 생성 | 법적 필수 항목(필수)과 실무 권장 항목(GPT권장)을 명확히 구분 |
| 비교 분석 | 항목별 대조표 형식 |

- 분류기는 GPT-4o-mini (저비용, 빠름, temperature=0.1)
- 답변 생성은 GPT-4o (고품질)
- 분류 → 검색 → 생성의 3단계로 각 단계의 역할을 명확히 분리

### 왜 GPT 기반 분류인가? (Rule-based 대비)
- 법률 질의는 표현이 다양하여 규칙 기반으로 7종을 구분하기 어려움
- "이거 되나요?" → 상황별 컨설팅 (규칙으로 잡기 어려운 패턴)
- GPT-4o-mini의 분류 비용은 질의당 약 $0.0001 수준으로 미미

## 5. 환각 방지: 왜 Grounding 원칙을 강제하는가?

### 문제
법률 도메인에서 LLM이 학습 데이터 기반으로 "그럴듯하지만 틀린" 답변을 생성하면, 사용자가 잘못된 법적 판단을 내릴 수 있습니다.

### 결정
모든 시스템 프롬프트에 Grounding Preamble을 삽입:

```
- 제공된 [해당 법령 정보]에 있는 내용만 답변하세요
- 정보가 없으면 "제공된 문서에서 찾을 수 없습니다"라고 명시하세요
- 추측하지 마세요. "일반적으로" 같은 모호한 표현을 사용하지 마세요
```

### 근거
- 법률 답변의 **정확성 > 완전성** — 모르는 것을 모른다고 하는 것이 틀린 답보다 나음
- 유형별로 Grounding 수준 차등 적용:
  - 법조문 조회: "문서에 있는 정확한 조문만 인용" (가장 엄격)
  - 문서 생성: 법적 필수 항목은 Grounding, 실무 권장은 GPT 판단 허용 (유연)
- 출처 표시를 강제하여 사용자가 직접 검증 가능

## 6. 임베딩 캐싱: 왜 MD5 해시 기반 캐시인가?

### 문제
OpenAI 임베딩 API는 호출당 비용이 발생하며, 동일한 텍스트를 반복 임베딩하는 것은 낭비입니다.

### 결정
텍스트의 MD5 해시를 키로 사용하는 Pickle 기반 로컬 캐시

### 근거
- 청킹 결과가 변경되지 않은 텍스트는 재임베딩 불필요
- MD5 해시로 텍스트 동일성 판별 → 캐시 히트 시 API 호출 생략
- 배치 100개 단위 처리로 API Rate Limit 준수
- 개발/테스트 반복 시 비용 절감 효과 큼

## 7. UI: 왜 Streamlit인가?

### 문제
POC 단계에서 빠르게 사용 가능한 웹 인터페이스가 필요합니다.

### 결정
Streamlit + `st.chat_message` 기반 채팅 UI

### 근거
- `st.chat_message`, `st.chat_input` 내장 → 채팅 UI 구현 비용 최소
- `@st.cache_resource`로 FAISS 인덱스, 리랭커 모델 로딩을 세션 간 공유
- 문서 생성 유형에 한해 `st.text_area` 편집기 + PDF/TXT 다운로드 제공
- POC → 프로덕션 전환 시 FastAPI + React로 교체 예정

## 요약: 전체 설계 원칙

1. **법률 도메인 특성 우선** — 범용 RAG가 아닌, 법률 구조를 인식하는 파이프라인
2. **정확성 > 완전성** — 환각 방지를 최우선으로 설계
3. **단계별 분리** — 각 단계가 독립적으로 테스트/교체 가능한 모듈 구조
4. **비용 효율** — 캐싱, 분류기 경량화, 리랭킹 후보 축소로 API 비용 최적화
